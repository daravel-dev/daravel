### Fixed

- A WebSocket whose handler waits on `socket.done` without listening, or writes in a loop while `socket.readyState` is open, now learns that its client closed or went away: while nothing reads the socket, the server goes on reading the client and holds what it sends, in order, for a listener to come (up to 64 KiB, or the route's `maxPayloadBytes` if smaller, plus one message, each held piece counted with a fixed cost and small frames held together; then TCP holds the client back). When the client's close or its going away has waited 5 s unread, the session ends with the client's code (1006 when it left without a close). When what is held is full and nothing has listened for 5 s, the server ends the session with 1008 and logs a warning with the path. Once the application listens, nothing is dropped: a listener that pauses gets every message and then the close. A `listen` after the server ended the session gets just the end.
- The server checks every frame a client sends as it arrives, whether the handler reads or not: an unmasked frame, a reserved opcode, RSV2 or RSV3, RSV1 without permessage-deflate or on a control or continuation frame, a fragmented control frame or one over 125 bytes, a close payload of one byte, a length not in its shortest form or with the top bit set, a continuation with no message, and a close code a client may not send (only 1000-1003, 1007-1014 and 3000-4999 are allowed) close the connection with 1002; a close reason that is not UTF-8 with 1007. The close the server answers with stays within 125 bytes, and `socket.closeCode` reports the client's code when its close was read, else the code the server closed with.
- A WebSocket closed as a slow client (its send buffer over `maxBufferedBytes`) ended its session up to 5 s after the connection was gone; now within 1 s.
