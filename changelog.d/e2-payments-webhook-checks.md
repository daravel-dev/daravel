### Fixed

- Security: `daravel_payments` compared a notification's amount with the order's but not its currency: a validly signed notification for 100 IDR paid an order of 100 USD. A notification whose currency differs from the order's (case aside) now changes nothing, answers `amountMismatch` and dispatches `PaymentAmountMismatch`; one without a currency is compared by amount only, as before. Since 1.0.0.
- Security: `MidtransGateway`, `StripeGateway` and `XenditGateway` accepted an empty or blank server key, webhook secret or callback token, with which anyone can sign or pass a notification. Such a key is now an `ArgumentError` when the gateway is made, and a blank `MIDTRANS_SERVER_KEY`, `STRIPE_WEBHOOK_SECRET`, `XENDIT_WEBHOOK_TOKEN` (or any other payment key) counts as unset, so the gateway reports its missing keys (`ConfigException`). stripe-php refuses an empty webhook secret too. Since 1.0.0.
- `daravel_payments` recorded a notification as handled even when it changed nothing, so the gateway's retry was answered `duplicate` and dropped: a notification that arrived before its order was stored never applied, and a Midtrans card `capture` held for review (`challenge`) hid the same `capture` once accepted, leaving the payment `pending`. Only a notification that moved the payment now counts as handled; one answered `unknownOrder`, `unchanged`, `ignored` or `amountMismatch` is looked at again when it comes back. A Midtrans event id now includes the signed order and `fraud_status` (`<order>:<transaction>:capture:accept`). A deadlock or serialization failure while applying runs the transaction again (up to three times). A notification for an order not stored yet is now answered 409 instead of 200, since the gateways send a notification again only after a non-2xx answer. Since 1.0.0.
- Security: Midtrans signs a notification's `order_id`, `status_code` and `gross_amount` only, and `daravel_payments` trusted its other fields: a validly signed `pending` notification (`status_code` 201) reporting `settlement` marked the payment paid, and since the event id was built from the unsigned `transaction_id` without the order, one validly signed notification for an order of one's own could carry another order's transaction id and have that order's genuine payment answered `duplicate` and never applied. The event id now holds the signed order (`<order>:<transaction>:<status>[:<fraud_status>]`), and only a payment is taken from the notification itself: `settlement` or `capture` with `status_code` 200 and a `fraud_status` that is empty or `accept`. Every other notification (`expire`, `cancel`, `deny`, `refund`, `partial_refund`, `chargeback`, `authorize`, `failure`, another `fraud_status`, another `status_code`, a status not known) is confirmed with Midtrans' status API, whose answer must be about the order asked for and a JSON object, and whose transaction id goes into the event id; when that API fails or answers otherwise the answer is 5xx and nothing is applied. One signed notification posted again within a minute reuses the API's answer (`MidtransGateway.confirmationWindow`, up to `confirmationMemoSize` answers per isolate), so it cannot make the application call Midtrans once per post. A notification without its `transaction_id`, or with an unsigned field of another type than text, answers 400. `pending` is still taken as it is: it moves no payment. A body that is not a JSON object answers 401, a Stripe body that is not UTF-8 401, a Stripe or Xendit status answer that is not JSON a `PaymentGatewayException`, and a signed amount of NaN or Infinity 400, none of them 500. Since 1.0.0.
- Security: a paid notification read by the Midtrans, Stripe or Xendit gateway without an amount and a currency it could read (a Stripe session without its currency, a Xendit invoice without `paid_amount`/`amount` or `currency`, a Midtrans `gross_amount` that is not a number) was applied without its amount compared. It is now refused with 400 and never applied, and the refusal is logged as a warning with the gateway, event id and order id (not the payload). Events an application builds and passes to `PaymentManager.apply` itself are unchanged: without an amount they are not compared. Since 1.0.0.

### Upgrade notes

- Upgrading can change webhook answers: a notification redelivered after it was answered `unknownOrder`, `unchanged`, `ignored` or `amountMismatch` is applied (or answered the same way again) instead of `duplicate`, including one stored by an earlier version as unprocessed; a Midtrans notification redelivered after the upgrade gets a new event id (it now holds the order) and is looked at once more: it finds the payment already in its status (`unchanged`) or past it (`ignored`), and changes nothing already applied. Constructing a gateway with an empty or blank key throws `ArgumentError`. No schema change.
- Upgrading can make a gateway resend notifications: one for an order not stored yet is answered 409, so Stripe, Midtrans and Xendit retry it. On a gateway account shared with another system, notifications for that system's orders are retried until the gateway gives up and show as failed in its dashboard; `withPayments(unknownOrderStatus: 200)` (or `Payment.webhookRoutes(..., unknownOrderStatus: 200)`) answers them 200 as before. A paid notification without a readable amount and currency gets 400, and a Midtrans notification without its `transaction_id` or with an unsigned field that is not text gets 400. Every Midtrans notification other than a payment (`settlement`/`capture` with `status_code` 200) and `pending` now makes one call to Midtrans' status API (an expiry, a cancellation, a refund, a challenged card), reused for a minute when the same notification comes again; while that API is down such notifications answer 5xx and Midtrans retries them. New public names: the `unknownOrderStatus` parameter of `withPayments` and `Payment.webhookRoutes`, `MidtransGateway.confirmationWindow` and `MidtransGateway.confirmationMemoSize`.
