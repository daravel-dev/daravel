### Fixed

- `daravel_payments` compares a payment's amount and currency with the order, applies status changes transactionally, and records only events that move the payment as handled. Gateway keys must be nonempty; Stripe and Xendit paid notifications without a readable amount or currency receive 400. Unknown orders receive 409 by default, configurable with `unknownOrderStatus` on `withPayments` or `Payment.webhookRoutes`.
- Payment order and event identifiers are checked against the 255 Unicode character storage limit before database access. Webhooks receive 400, and application calls to `Payment.checkout` and `PaymentManager.apply` throw `ArgumentError` for longer identifiers before the gateway or the database is reached. JSON log payloads larger than 65,535 UTF-8 bytes store a size marker while the event retains its raw data, without a schema migration.
- A Midtrans status answer with a paid status and no readable `gross_amount` is a gateway failure: the webhook receives 5xx and `status()`/reconciling throws `PaymentGatewayException`, so a payment is never marked paid without its amount compared. A Midtrans notification whose `transaction_id` is longer than 255 characters, or whose order or transaction id is `.` or `..`, receives 400 before any lookup. `MidtransGateway.status(orderId, reference:)` looks the order up by `reference` when Midtrans does not know it by its id; a reference that is blank, the order id itself, longer than 255 characters, `.` or `..` is not looked up.

### Changed

- Every verified Midtrans notification obtains its event from the status API for the authenticated order. A missing order lookup permits one transaction-id lookup, whose answer must still match that order. Status responses require a transaction id, status and code 2xx or 407 with `expire`; invalid or unavailable responses receive 5xx without applying an event. Per order, one batch of lookups runs and one waits for arrivals during it; a batch looks the order up once and, when Midtrans does not know it by its id, each distinct transaction id in turn (at most four, so at most five outgoing calls), each notification getting the answer for its own transaction id. A fifth distinct transaction id while the waiting batch is full receives 429 with `Retry-After: 1`. Completed responses are not cached.

### Upgrade notes

- Midtrans webhook handling requires outbound status API access for every verified notification, including `pending`, `settlement` and `capture`. Fake the status API (`/v2/*/status`) in webhook tests, allow outbound HTTPS in production, configure ingress rate limits, and handle 5xx responses during gateway outages. A missing order lookup is followed once by a transaction-id lookup; two missing answers receive 5xx. Direct `status(orderId)` calls continue to return `pending` for missing transactions.
- Midtrans event ids use `<order>:<transaction>:<status>[:<fraud_status>]` from the API response. Retries of events recorded with earlier identifiers can be evaluated again against the current payment state. Because the event id holds the order id, a Midtrans order id must leave room for the transaction id and status within 255 characters (Midtrans allows 50 characters for a Snap order id). `unknownOrderStatus: 200` acknowledges unknown orders when a gateway account is shared with another system.
- Stripe and Xendit notifications in another currency than the order are now `amountMismatch`, and a Midtrans notification without a text `transaction_id` receives 400.
- Webhook log rows store `{"truncated":true,"bytes":N}` above 65,535 UTF-8 bytes; listeners still receive the full `raw` payload.
- An `amountMismatch` notification delivered again is checked again and dispatches `PaymentAmountMismatch` again (with another status call for Midtrans): make its listeners idempotent.
- On MySQL, event ids that differ only in letter case are one event under the default collation; PostgreSQL and SQLite keep them apart.
