### Fixed

- Security: `daravel_payments` compared a notification's amount with the order's but not its currency: a validly signed notification for 100 IDR paid an order of 100 USD. A notification whose currency differs from the order's (case aside) now changes nothing, answers `amountMismatch` and dispatches `PaymentAmountMismatch`; one without a currency is compared by amount only, as before. Since 1.0.0.
- Security: `MidtransGateway`, `StripeGateway` and `XenditGateway` accepted an empty or blank server key, webhook secret or callback token, with which anyone can sign or pass a notification. Such a key is now an `ArgumentError` when the gateway is made, and a blank `MIDTRANS_SERVER_KEY`, `STRIPE_WEBHOOK_SECRET`, `XENDIT_WEBHOOK_TOKEN` (or any other payment key) counts as unset, so the gateway reports its missing keys (`ConfigException`). stripe-php refuses an empty webhook secret too. Since 1.0.0.
- `daravel_payments` recorded a notification as handled even when it changed nothing, so the gateway's retry was answered `duplicate` and dropped: a notification that arrived before its order was stored never applied, and a Midtrans card `capture` held for review (`challenge`) hid the same `capture` once accepted, leaving the payment `pending`. Only a notification that moved the payment now counts as handled; one answered `unknownOrder`, `unchanged`, `ignored` or `amountMismatch` is looked at again when it comes back. A Midtrans event id now includes `fraud_status` (`<transaction>:capture:accept`). A deadlock or serialization failure while applying runs the transaction again (up to three times). A notification for an order not stored yet is now answered 409 instead of 200, since the gateways send a notification again only after a non-2xx answer. Since 1.0.0.
- Security: a Midtrans notification's `transaction_status` is not covered by its signature, and a validly signed `pending` notification (`status_code` 201) reporting `settlement` marked the payment paid. The status must now agree with the signed code (200 for `capture` and `settlement`, 201 `pending`, 202 `deny`, 407 `expire`, from Midtrans' status codes reference; statuses the reference pairs with no code for every payment method are not checked); otherwise 401 and nothing changes. Since 1.0.0.
- Security: a paid notification read by the Midtrans, Stripe or Xendit gateway without an amount and a currency it could read (a Stripe session without its currency, a Xendit invoice without `paid_amount`/`amount` or `currency`, a Midtrans `gross_amount` that is not a number) was applied without its amount compared. It is now refused with 400 and never applied, and the refusal is logged as a warning with the gateway, event id and order id (not the payload). Events an application builds and passes to `PaymentManager.apply` itself are unchanged: without an amount they are not compared. Since 1.0.0.

### Upgrade notes

- Upgrading can change webhook answers: a notification redelivered after it was answered `unknownOrder`, `unchanged`, `ignored` or `amountMismatch` is applied (or answered the same way again) instead of `duplicate`, including one stored by an earlier version as unprocessed; a Midtrans notification with a `fraud_status`, redelivered after the upgrade, gets a new event id and is looked at once more (it finds the payment in its status: `unchanged`). Constructing a gateway with an empty or blank key throws `ArgumentError`. No schema change.
- Upgrading can make a gateway resend notifications: one for an order not stored yet is answered 409, so Stripe, Midtrans and Xendit retry it. On a gateway account shared with another system, notifications for that system's orders are retried until the gateway gives up and show as failed in its dashboard; `withPayments(unknownOrderStatus: 200)` (or `Payment.webhookRoutes(..., unknownOrderStatus: 200)`) answers them 200 as before. A Midtrans notification whose `transaction_status` disagrees with its `status_code` gets 401, and a paid notification without a readable amount and currency gets 400. New public names: the `unknownOrderStatus` parameter of `withPayments` and `Payment.webhookRoutes`, and `MidtransGateway.signedStatusCodes`.
