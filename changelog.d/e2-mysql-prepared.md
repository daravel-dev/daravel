### Added

- `DB.unprepared(sql)` (Laravel's `DB::unprepared`), `DatabaseManager.unprepared`: runs a script of several statements, or one the server cannot prepare, on MySQL/MariaDB (text protocol), PostgreSQL (simple query protocol) and SQLite (`sqlite3_exec`). Drivers expose it through the `UnpreparedExecutor` interface. `SqlTextException` (`MultipleStatementsException`, `NoStatementException`, `NulInSqlException`) is a driver's refusal of SQL text for its shape, reported as a `QueryException`. `dartisan lint` (`no_sql_string_interpolation`) checks `unprepared` too.

### Fixed

- Security: on MySQL and MariaDB, `DB.select`, `DB.statement` and `DB.insertGetId` without bindings ran every statement in their SQL (`SELECT 1; DROP TABLE users`): `mysql_dart` sends such a statement as text on a connection that announces multi-statement support. Each new text without bindings is now checked with a prepare, closed at once, and remembered per connection (256 texts of up to 4 096 characters), so a second statement fails with the server's syntax error and nothing runs. Laravel prepares these statements (`ATTR_EMULATE_PREPARES => false`). A `SET`, `CALL`, `EXECUTE` or MariaDB `BEGIN NOT ATOMIC` makes the connection check its texts again, also behind comments and inside executable comments (`/*!40101*/ SET`, `/*M!100616 SET … */`), since `sql_mode` and the character set change how text splits; a trigger or stored function that changes `sql_mode` is not noticed. A statement the prepared protocol does not support (1295) runs as text, as `pdo_mysql` falls back for it, and is checked every time. A repeated text costs nothing extra; a text new to a connection costs one more round trip. Since 1.0.0.
- Security: on MySQL and MariaDB, SQL holding a NUL character is refused before it is sent (`NulInSqlException`): the server read the NUL as the end of the text, so `SELECT 1` followed by a NUL and more ran as `SELECT 1`, and two statements split by a NUL ran the first before failing. Since 1.0.0.
- Security: on SQLite, `DB.statement` and `DB.insertGetId` without bindings ran every statement in their SQL (`sqlite3_exec`). They now refuse a second statement, as `select` and every call with bindings already did, with a `QueryException` whose `previous` is a `MultipleStatementsException` (`select`'s refusal used to escape as a bare `ArgumentError`). Laravel on SQLite runs the first statement and drops the rest without an error; refusing is deliberate. SQL holding no statement (empty, a comment, `;`) still does nothing in `statement` and `insertGetId`, which now answer 0 rows and no id instead of the previous statement's; in `select` it is a `QueryException` (`NoStatementException`) instead of a bare `ArgumentError`. Since 1.0.0.
- On SQLite, SQL holding a NUL character made `select` loop for ever inside `package:sqlite3`, and `DB.unprepared` silently ran only what came before the NUL; it is now refused before it reaches SQLite (`NulInSqlException`).

### Upgrade notes

- Upgrading can break a migration or seeder that runs several statements in one `DB.statement` (SQLite, MySQL, MariaDB): run such a script with `DB.unprepared`. SQL holding a NUL character is refused on SQLite, MySQL and MariaDB. New public names: `DB.unprepared`, `DatabaseManager.unprepared`, `UnpreparedExecutor`, `SqlTextException`, `MultipleStatementsException`, `NoStatementException`, `NulInSqlException`, `MySqlDriver.unprepared`, `MySqlDriver.singleStatementCacheSize`, `MySqlDriver.singleStatementMaxLength`, `MySqlDriver.changesSplitting`, `SqliteDriver.unprepared`, `PostgresDriver.unprepared`.
