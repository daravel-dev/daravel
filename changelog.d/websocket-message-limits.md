### Added

- `router.ws` and `Response.webSocket` take `assembleTimeout` (`Response.defaultWebSocketAssembleTimeout`, 30 s: how long a message, in one frame or in fragments, may take to arrive once it began), `controlFrameBurst` (`Response.defaultWebSocketControlFrameBurst`, 20) and `controlFramesPerSecond` (`Response.defaultWebSocketControlFramesPerSecond`, 5): how many PING and PONG frames a client may send, as a burst and then per second, before the connection is closed with `1008`. `Response.webSocketAssembleTimeout`, `Response.webSocketControlFrameBurst` and `Response.webSocketControlFramesPerSecond` read them.

### Fixed

- Security: a WebSocket client could make a worker hold more memory than the route's limits allow. The server now reads WebSocket frames itself before handing them on: a message is limited as a whole, all its fragments together (`maxPayloadBytes`, closed with `1009`); a message must arrive within `assembleTimeout` (`1008`); PING and PONG frames are rate limited per connection (`1008`); what waits to be written, control frames included, counts toward `maxBufferedBytes`; and a control frame between fragments is handled apart from the message. A connection closed for a violation is read only a little further, and a connection whose client went away while the server was writing ends. Messages in one frame pass unchanged; permessage-deflate, `pingInterval` and the slow-client close codes behave as before. Since 1.14.0 for fragmented messages (before it, no message limit applied), since 1.6.0 for control frames. Until you upgrade, limit WebSocket connections and handshakes per client IP at the proxy (nginx `limit_conn` and `limit_req` on the upgrade location); a proxy does not limit WebSocket frames.
- A WebSocket session ended only when the server stopped if its handler neither wrote nor closed, even after the client closed or dropped the connection: each such connection kept its scope and its slot in the server's count of open WebSockets. The socket is now closed from the server side when the client goes away. Since 1.6.0.

### Upgrade notes

- The Pusher server closes a message above `REVERB_APP_MAX_MESSAGE_SIZE` with `1009`, as Reverb does; it allowed 1 KiB more before.
- Incoming WebSocket messages cost a few percent more (2 to 10 % for 1 KB messages, 4 to 6 % for 64 KB, in a local benchmark); sending is not affected.
- A client that sends PING frames faster than 20 at once and then 5 a second is now closed with `1008`. Browsers never send PINGs; raise `controlFrameBurst` and `controlFramesPerSecond` on routes whose clients ping often.
- New public names in `package:daravel/daravel.dart`: `Response.defaultWebSocketAssembleTimeout`, `Response.defaultWebSocketControlFrameBurst`, `Response.defaultWebSocketControlFramesPerSecond`, `Response.webSocketAssembleTimeout`, `Response.webSocketControlFrameBurst`, `Response.webSocketControlFramesPerSecond`, and the `assembleTimeout`, `controlFrameBurst` and `controlFramesPerSecond` parameters of `Response.webSocket` and `router.ws`.
