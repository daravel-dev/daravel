### Added

- Rolling restarts (Blueprint #135, after R3). `Supervisor.rollingRestart({readyTimeout})` restarts the workers one at a time, the next only once the previous one's replacement is ready, so the server keeps accepting connections; `readyTimeout` (30 s) counts from the old worker's exit, whose drain is bounded as at shutdown. A replacement that is not ready in time, or fails, stops the round there and the other workers serve on; a worker respawning already is skipped, and while stopping every worker is. One round at a time: calls during a round make one more round after it. The result is a `RollingRestart` (`WorkerRestartOutcome` per worker, `WorkerRestartStatus`), logged and dispatched as `WorkersRestarted` in the main isolate. `ApplicationBuilder.withSupervisorHook(SupervisorHook)` runs code in the main isolate once the workers started, with its booted application (kept only while a hook returned a stop function) and the supervisor; a hook's errors are logged. `Application.supervised` is true in a supervisor's workers (`markSupervised()`). `daravel_reverb`: with several isolates, `reverb:restart` is heard once by the main isolate, through one signal store connection, and rolls the workers; with one isolate nothing changes.

### Upgrade notes

- Supervisor (rolling restart): new public names `RollingRestart`, `WorkerRestartOutcome`, `WorkerRestartStatus`, `WorkersRestarted` and `SupervisorHook` in `package:daravel` (an application class of one of these names and the barrel import give an ambiguous-import error; `hide` it or rename yours). `daravel_reverb` with several isolates: `reverb:restart` no longer restarts every worker at about the same moment; the main isolate keeps one signal store connection while `reverb:start` serves.
