### Added

- `DashboardGate` (`package:daravel`): the one rule of the dashboards (Horizon, Pulse, Reverb, the log viewer). `DashboardGate.allows(request, ability:, name:, callback:)` passes in `APP_ENV=local`, else asks the callback when there is one, else the gate `ability` when it is defined; anything else is no, a callback or gate that throws is no (logged), and it never throws. `DashboardGate.middleware(registry, given, setup:, authHint:)` chooses what a dashboard sits behind: the given middleware when the application registers it (else a `ConfigException` naming `withSession()` and the callback), without it the `web` group when there is one.
- `Pulse.auth((request) => ...)`, `ReverbDashboard.auth((request) => ...)` and `LogViewer.auth((request) => ...)`: who may open the dashboard outside `APP_ENV=local`, before the gate (`viewPulse`, `viewReverb`, `viewLogViewer`), for applications without sessions; kept per isolate, so call them inside `createApp`. `Pulse.auth` is a Daravel addition (Laravel Pulse has only the gate); `LogViewer.auth` is opcodesio/log-viewer's `LogViewer::auth`.

### Changed

- Pulse, the Reverb dashboard and the log viewer decide who may see them as the Horizon dashboard does (`DashboardGate`): open in `APP_ENV=local` only; elsewhere, `APP_ENV=testing` included, every route (Pulse's page and API; Reverb's page, tabs, stats, apps, stream and restart; the log viewer's page, files, entries, tail, download and delete) answers 403 unless the callback or the gate allows the request. Middleware never opens a dashboard any more: `withPulse`, `withReverb` and `withLogViewer` take `middleware: List<Object>?`, run it before that decision, and without it put the dashboard behind the `web` group when the application has sessions. `dartisan pub:add pulse`, `reverb` and `log-viewer` register `.withPulse()`, `.withReverb()` and `.withLogViewer()` and print the gate and the callback as next steps. Horizon moved onto `DashboardGate` without a change of behaviour.
- Horizon dashboard: a master status whose workers are not maps no longer fails `/api/stats` and `/api/workload` (those workers are on no queue); with `HORIZON_PATH=/`, a path that is not a tab is no longer the dashboard's (the application's own route answers, or 404) instead of a 403; `starting_at` is held at `HorizonDashboard.maxOffset` (100 000), so the pending list's count of a skipped queue reads at most 17 jobs one by one.
- `dartisan security:audit` (DARAVEL-SEC-012) advises upgrading `daravel_log_viewer` and its gate or callback, no longer middleware.

### Upgrade notes

- Pulse (published since 1.16): a dashboard opened outside `APP_ENV=local` by middleware alone (`withPulse(middleware: ['throttle:60'])`, or `['auth']` without `can:viewPulse`) answers 403 until the `viewPulse` gate or `Pulse.auth` allows the request. The snippet earlier installers wrote, `withPulse(middleware: ['auth', 'can:viewPulse'])`, works as before: the application defines the gate, which now decides a second time. Without `middleware:` it was 403 outside local and stays so unless the gate or callback allows; `APP_ENV=local` stays open.
- Pulse, Reverb dashboard and log viewer: tests that opened a dashboard under `APP_ENV=testing` get 403; set the callback (`Pulse.auth((request) => true)`, reset to null in `tearDown`) or define the gate in the test.
- Log viewer: unlike opcodesio/log-viewer, an environment other than local (staging) without the gate or callback is closed, not open. The gate is `viewLogViewer` (the earlier guide's `view-logs` was an example name: rename it, or keep it and call `Gate.allows('view-logs')` from `LogViewer.auth`).
- New public names `DashboardGate` in `package:daravel`, `Pulse.auth`, `ReverbDashboard.auth`, `LogViewer.auth` and `HorizonDashboard.maxOffset`; an application class named `DashboardGate` and the barrel import give an ambiguous-import error (`hide` it or rename yours).
