### Fixed

- Security: `daravel_medialibrary` decoded an image for its conversions whatever size it declared: a 995 368-byte PNG of 16 000 x 16 000 RGBA pixels took 2.2 GiB of memory (an isolate shares its process's memory), and other formats could do the same. Images are now decoded only as JPEG, PNG, GIF, WebP or BMP, told from the content, each by a decoder held to `MEDIA_MAX_IMAGE_PIXELS` (40 million pixels, width x height x frames; a 16-bit PNG and a WebP count twice) and `MEDIA_MAX_IMAGE_FRAMES` (1 000), with the size read from the header before anything is decoded; a still image is decoded as its one frame, and a JPEG must have 1 or 3 color components. Past a limit, `ImageTooLargeException`: the conversion is not made, the job fails at once instead of three times, and the original stays stored (the same PNG now peaks at 16 MiB). The EXIF orientation is baked only when there is one to apply. Since 1.0.0.
- Security: TIFF is not converted in this version: a TIFF keeps its original and gets no conversions, and `canConvert` answers `false` for it. Animated PNG (APNG) and animated WebP are not converted in this version either: such a file keeps its original and gets no conversions (`ImageConversionException`); a still PNG or WebP and an animated GIF are converted. ICO, TGA, PVR, EXR, PNM and PSD content is not converted either, whatever the file is named.
- Security: image conversions bound the work of decoding and manipulating an image. Every image made by a resize, crop or canvas holds at most a quarter of `MEDIA_MAX_IMAGE_PIXELS` (frames counted), an image read or made has sides of at most 65 535, and a progressive JPEG with more scans than its size allows is not converted. The whole conversion (decoding, turning the image upright, every manipulation, writing, each counted for every frame) is planned from the image's header before anything is decoded and refused past `MEDIA_MAX_CONVERSION_WORK` (10 000 work units; a unit is at most about a millisecond of one core of the slowest CI runner measured, a GitHub Actions `ubuntu-latest` runner with an AMD EPYC 7763); a combination of format, pixels and step without a measured cost is refused. Invalid manipulation dimensions are rejected consistently and image encoder errors use `ImageConversionException`; past a limit, `ImageTooLargeException`. Since 1.0.0.
- `Fit.fill` and `Fit.fillMax` on an animated GIF keep every frame, each with its duration, on the white canvas; they kept only the first.
- The JPEG scan count before decoding skips what the segments before the first scan carry (an EXIF thumbnail, a comment), as a decoder does, so bytes there are no longer counted as scans.
- A manipulated 16-bit image is made 8-bit first, as GD (laravel-medialibrary's default driver) holds it; one only written in another format keeps its 16 bits, and a 16-bit image is written as a GIF through 8 bits, which the GIF encoder could not take. A 1, 2 or 4-bit image is made 8-bit before greyscale or blur.
- An `Error` the image library throws reading, decoding or encoding a file becomes an `ImageLibraryException` (an `ImageConversionException`) with the error's type, logged as a warning: the conversion job fails once instead of decoding the same file three times. Running out of memory or stack is thrown as it is.

### Upgrade notes

- Upgrading can leave conversions ungenerated: for TIFF files and animated PNG or WebP files (until a later version; the original stays stored), for an image larger than 40 million pixels (width x height x frames) or with more than 1 000 frames (raise `MEDIA_MAX_IMAGE_PIXELS` / `MEDIA_MAX_IMAGE_FRAMES` if such images are expected), and for image content other than JPEG, PNG, GIF, WebP and BMP whatever the file is named; the failed conversion job holds the reason. `MEDIA_MAX_IMAGE_PIXELS`, `MEDIA_MAX_IMAGE_FRAMES` or `MEDIA_MAX_CONVERSION_WORK` below 1 stops the boot. `ImageConversionException` is now a `base` class. New public names: `ImageTooLargeException`, `MediaLibraryConfig.maxImagePixels`, `MediaLibraryConfig.maxImageFrames`, `MediaLibraryConfig.defaultMaxImagePixels`, `MediaLibraryConfig.defaultMaxImageFrames`, `MediaLibraryConfig.maxConversionWork`, `MediaLibraryConfig.defaultMaxConversionWork`, and the `maxPixels`/`maxFrames`/`maxWork` parameters of `convertImage`/`convertImageSync`.
- Upgrading can leave conversions ungenerated for an image with a side longer than 65 535 pixels, for any resize, crop or canvas output past a quarter of `MEDIA_MAX_IMAGE_PIXELS` (10 million pixels at the default; 1080p to 4K still converts), for a non-positive manipulation dimension, for a JPEG with more scans than its size allows, or for a conversion estimated past `MEDIA_MAX_CONVERSION_WORK` (10 000 units by default); the original file stays stored. At the defaults the pixel limit refuses large photos first (a 40-megapixel JPEG resized to a width of 1 600 is 6 617 units, 3.1 s on that runner); the work budget refuses long chains, heavy blur, large GIF output and large 16-bit work: the longest measured chain (enlarge a small PNG to 10 million pixels, crop, fill, blur 30, write a GIF) is 16 132 units, 12.0 s on that runner. Raise `MEDIA_MAX_CONVERSION_WORK` to allow more; a machine slower than that runner takes longer for the same units. Put `width` or `height` before `blur` when a conversion needs both.
- Upgrading can leave a photo above 40 million pixels (a phone's 48 or 50 MP mode, for example) without conversions unless `MEDIA_MAX_IMAGE_PIXELS` is raised; the original file stays stored.
- Upgrading can leave a WebP above 20 million pixels without conversions at the default limit, since a WebP counts against half of `MEDIA_MAX_IMAGE_PIXELS`; raise it to twice the largest WebP expected. The original file stays stored.
- Converting an image at the default limit still takes memory: about 130 MiB for a baseline JPEG of 8 000 x 5 000, about 415 MiB for a progressive one, about 205 MiB for a PNG of 6 324 x 6 324, up to about 470 MiB for a WebP, and about 140 MiB for an animated GIF filling the budget (measured peaks); plan about 500 MiB per conversion running at once, whatever the size of the image, since the limit bounds an image's size, not memory exactly; lower `MEDIA_MAX_IMAGE_PIXELS` where conversions share a process with requests.
- A manipulated 16-bit PNG now comes out 8-bit, as with laravel-medialibrary's default GD driver; a 16-bit PNG converted without manipulations still comes out 16-bit. Run conversions on the queue with a bounded number of workers and a job timeout above what `MEDIA_MAX_CONVERSION_WORK` takes on the machine: nothing else limits how many run at once, and `nonQueued()` conversions run in the request that adds the file.
