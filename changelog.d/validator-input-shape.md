### Fixed

- Security: `validated()` read a map key from the client as a list index when it looked like a number. `{"items": {"20000000": "a"}}` (or the form `items[20000000]=a`) against `items.*` built a list of 20 000 001 entries, and `"-1"` failed with a `500`. Each level of `validated()` now has the shape it has in the input: a map stays a map with its keys as sent, a list stays a list, and no key decides the length of a list.
- Security: a `.` or `*` in a key of the data was read as a level or a wildcard, so `{"items": {"a.b": {"role": "admin"}}}` passed `items.*.role` against `in:member` without the rule running. Such keys are now keys, as in Laravel (which replaces them with placeholders while the rules run): the rules under a wildcard apply to that element, and its error is reported under the key as sent (`items.a.b.role`).
- Security: an empty key under a top-level wildcard was skipped, so `{"": {"role": "admin"}}` passed `*.role` against `in:user`. A `*` now matches an empty key at every level, as in Laravel, and the error is reported under `.role`.
- A list index written in a rule key is read only in its canonical form: `items.-1.*` no longer fails with a `500`, and `items.01.name` names the key `01` (as in PHP), not the element at index 1, in every lookup and in `validated()`.

### Upgrade notes

- `validated()` keeps a JSON object as a map also when its keys are numbers: `{"items": {"0": "a", "1": "b"}}` used to come out as the list `["a", "b"]` and now comes out as that map. JSON lists and form fields (`items[0][name]`, already a list) are unchanged. Under an `array` rule, `ValidatedData.list()` still reads a map keyed `"0"`, `"1"`, ... in order as a list; any other map throws a `StateError` (a `500`), so give the field the `list` rule to answer `422` (it takes only a list).
- Rules see the data as sent, keys with a `.` or `*` included: every rule, a `Rule` class of the application as well as a closure (`Rules.custom`), gets `ValidationContext.attribute` and the value as sent, as Laravel hands a rule object its original attribute; `root`, `has` and `sibling` find other fields, and their values are as sent too, so two fields compare in one form. A `forEach` callback gets its value and attribute as sent, and the rules that compare keys (`required_array_keys`, `array:a,b`, `in_array_keys`, `array_keys`) compare the keys the client sent with the ones written in the rule, so `required_array_keys:a.b` is met by `{"a.b": 1}` (in Laravel a dotted parameter of these rules matches no key). Build no path from `attribute` to look data up: `meta.a.b` reads as three levels.
