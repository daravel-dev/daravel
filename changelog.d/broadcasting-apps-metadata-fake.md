### Added

- Several Pusher applications on one server (Blueprint #135, R2a), as Reverb's `reverb.apps.apps`: `withBroadcasting(apps:)` takes a `BroadcastAppProvider` (`byKey`, `byId`), such as `ListAppProvider([BroadcastApp(id:, key:, secret:, allowedOrigins:, maxConnections:, maxMessageSize:, activityTimeout:, encryptionMasterKey:, rateLimiting: BroadcastRateLimit(...))])`. Each application has its own secret (channel authorizations and the signed HTTP API), origins, connection quota (counted per application in the coordinator), message size and rate limiting, and the same channel name in two applications is two channels; the HTTP API lists only the application's own. Without `apps:` the server serves the `REVERB_APP_*` application through `SingleAppProvider.fromConfig`, and that application's channels, state and wire format are as before. `PusherServer(apps:)`, `PusherServer.apps`, `topicOf` and `channelOf`. Channels describe themselves: `channels.channel(pattern, authorize, type: 'private' | 'presence' | 'encrypted', events: [BroadcastEventSchema(name, data: JsonSchema...)])`, `ChannelRegistry.describe()` (`ChannelDescription`), `Application.broadcastChannels` and `dartisan route:list --channels [--json]`; they change nothing at run time. Guide: [Broadcasting](docs/guide/broadcasting.md#several-applications).
- Testing and watching broadcasts (Blueprint #135, R2b). `Broadcast.fake()` (`BroadcastManager.fake()`, `restore()`, `faked`) records `BroadcastRecord`s (event, channels, data, the connection left out, the `ShouldBroadcast` it came from) instead of sending, after the transaction rules, so a broadcast rolled back is not recorded; `BroadcastFake` has `broadcasted<E>()`, `named()`, `assertBroadcasted<E>(channel:, where:)`, `assertBroadcastedTimes<E>`, `assertSent(name)`, `assertNotBroadcasted<E>`, `assertNothingBroadcastedTo(channel)` and `assertNothingBroadcasted()` (Laravel tests broadcasts with `Event::fake()`). `/metrics` gains `reverb_connections{app,worker}`, `reverb_channels{app,type}`, `reverb_messages_total{app,direction}` and `reverb_fanout_seconds{app}` (`AppMetrics.recordReverbConnection`, `recordReverbSubscription`, `recordReverbMessage`, `recordReverbFanout`). `PusherObserver` (`PusherServer(observer:)`, `PusherObservers`) is told about connections, subscriptions, messages, fan-out and refusals per application; `ReverbStats` reports each isolate's activity to the coordinator as `WorkerReports` topic `reverb` every `REVERB_PULSE_INGEST_INTERVAL` seconds (`BroadcastConfig.pulseIngestInterval`, 15, as Reverb) while it has connections, and `daravel_pulse` shows it as a *Reverb* card (`Pulse.reverb`). Guide: [Broadcasting](docs/guide/broadcasting.md#testing-broadcasts).

### Upgrade notes

- Broadcasting (R2a): a channel name containing `:` is refused even with `REVERB_APP_VALIDATE_CHANNEL_NAMES=false` (`pusher:error` `4300` on subscribe, `422` from the HTTP API, an `ArgumentError` from `PusherServer.publish`), because `:` now separates another application's channels; Pusher never allowed it. New public names `BroadcastApp`, `BroadcastAppProvider`, `SingleAppProvider`, `ListAppProvider`, `BroadcastRateLimit`, `BroadcastEventSchema` and `ChannelDescription` in `package:daravel` (an application class of one of these names and the barrel import give an ambiguous-import error; `hide` it or rename yours). The connection quota and rate limiting of a connection now come from its application (`BroadcastApp`), which for the `REVERB_APP_*` application are the same `REVERB_APP_*` values.
- Broadcasting (R2b): `reverb_rejected_total` gains an `app` label (`{app="42",reason="rate_limit"}`), so a dashboard or alert matching the exact old series `{reason="..."}` needs `sum without (app)`. New public names `BroadcastFake`, `BroadcastRecord`, `PusherObserver`, `PusherObservers` and `ReverbStats` in `package:daravel` (same remedy: `hide` or rename). The application's `PusherServer` no longer sets `onRejected` (its metrics come through `observer`); a `PusherServer` built in code keeps `onRejected` as before.
